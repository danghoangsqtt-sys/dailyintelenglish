## Summary
`app/services/script_service.py::update_script_line` (called by `regenerate_line` for
single-line AI regeneration, and by any other future caller updating one line's text)
only sets `text` and `language_notes`:
`UPDATE script_lines SET text = ?, language_notes = ? WHERE id = ? AND project_id = ?`
— it never clears `audio_cache_path` or `duration_seconds`, which still point at
audio synthesized from the *old* text.

Note: the full-script save path (`save_script`, used by `generate_script` and manual
full-script save) is **not** affected — it deletes and re-inserts every line with a
fresh UUID, so those lines correctly start with no cached audio.

**Mitigating factor** (same as BUG-016): both real consumption paths (per-line
"Listen", "Generate All") always re-synthesize fresh audio before playing/mixing, so
the actual audio a user hears/downloads is never wrong. The real, narrower observable
effect: the TTS/Video timeline's proportional clip-width visualization
(`step4_tts.js`/`step5_video.js`'s `measuredClipWidth`, from Task 5.2) reads
`state.audioJob.timestamps` — the *last full mix's* timing — which can show a stale
clip width for the regenerated line until "Generate All" is re-run. This is a purely
visual staleness in an already-known-stale state (Task 7.1's `mark_script_changed()`
already downgrades project status on any script line regenerate, so the UI already
signals "downstream needs regeneration" at the project level).

## Details
- **Tier**: 3 (data hygiene / minor correctness)
- **Affected files**: `app/services/script_service.py` (`update_script_line`)
- **Verification method**: read `update_script_line`'s SQL directly; cross-referenced

  calculation (not `script_lines.duration_seconds` directly).
