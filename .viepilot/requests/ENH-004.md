## Summary
`app/db/database.py`'s `Database` class is a process-wide singleton wrapping exactly
one shared `aiosqlite.Connection` (confirmed via direct read: `connect()` opens the
connection once and caches it; `get_db()` always returns the same connection object).
No connection pool exists. No `PRAGMA journal_mode=WAL` is set (grepped the whole
`app/` tree for `journal_mode`/`WAL`/`PRAGMA` — only `PRAGMA foreign_keys = ON` is
present). `aiosqlite` internally serializes all operations against a single connection
through its own background thread, so every DB read and write across every concurrent
request queues behind this one connection.

## Corrected finding (2026-09-18, re-investigated under Phase 8 / Task 8.1)

Re-investigation found the original finding's *shape* was accurate (one shared
connection, no pool, no WAL) but the *implied fix* (enable WAL, or add a pool) would
not actually do anything useful here — and PM should have caught this the first time,
since the original ENH-004 grep already listed `app/api/projects.py` as one of the 18
files touching the connection, but its `Lock`/`asyncio.Lock` usage wasn't read closely
enough at the time.

`app/api/projects.py` lines 20-36 contain an existing, detailed code comment
explaining that the whole app **already** serializes every route — reads included —
on one connection-wide `asyncio.Lock` (`_write_lock`), specifically *because* there is
exactly one shared connection and SQLite does not support nested transactions on a
single connection (a dirty read or phantom read would otherwise be possible across
concurrent requests sharing one connection's single implicit transaction). This is not
an accidental gap; it is the correct, already-reasoned defense against the exact
hazard a single connection creates.

Given that, `PRAGMA journal_mode=WAL` would be **purely cosmetic**: WAL's real benefit
(concurrent readers not blocking behind a writer) only manifests when readers and the
writer use *separate* connections. Since every request already funnels through the
same one connection, serialized in Python by `_write_lock`, WAL would not relax that
serialization at all — only add `-wal`/`-shm` sidecar files and checkpoint behavior for
zero measurable gain. A change that would actually alter the concurrency
characteristics here means replacing `_write_lock` with a real connection-pool
architecture (one connection per request, and re-deriving every route's isolation
guarantees from scratch) — a genuinely large architectural change, not a quick win,
and explicitly the kind of change this project has consistently deferred for a solo
local-use, single-user app (same standing as Progress cancellation and real
LivePortrait lip-sync).

**Decision: `wontfix` for now.** No code changed for this item. Re-open only if real
multi-request concurrent load ever becomes a genuine, observed problem for this app —
at which point the fix is the connection-pool redesign described above, not WAL alone.
