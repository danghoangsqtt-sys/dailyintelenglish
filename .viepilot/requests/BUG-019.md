# BUG: Avatar upload's filesystem mutation isn't rolled back if the surrounding DB transaction later fails

## Meta
- **ID**: BUG-019
- **Type**: Bug
- **Status**: open (logged, not scoped into Phase 9 per user decision)
- **Priority**: medium (real architectural gap; low real-world likelihood for a
  single-user local app — requires a genuine SQLite commit failure, not a normal
  request path)
- **Created**: 2026-09-18
- **Reporter**: Codex (parallel read-only vp-audit pass, requested alongside PM's own audit)
- **Assignee**: unassigned
- **Source**: Codex's independent read-only audit, independently re-verified by PM

## Summary
`app/services/avatar_service.py::upload_avatar` calls `_finalize_avatar_file` (line
78), which **deletes the previous avatar file and renames the new upload into place
on disk**, *before* the corresponding `UPDATE speakers SET avatar_image_path = ?`
statement runs and *before* the surrounding `_write_transaction`'s `db.commit()`
executes. SQLite's transactional atomicity only covers the database itself, never the
filesystem. PM confirmed via direct code read: if `db.commit()` (or any statement
after the finalize call) were to fail — a real, if rare, possibility (disk I/O error,
corruption, etc.) — `_write_transaction`'s `except: await db.rollback(); raise`
would roll back the `UPDATE speakers` statement, but by then the *old* avatar file is
already permanently deleted and the *new* file is already in place. Result: the DB
would still reference the old (now-deleted) file path, while the actual new file
sits on disk under a path the DB doesn't know about — a dangling reference plus an
orphaned file.

Codex's report describes testing this by forcing a rollback and observing exactly
this broken state.

## Details
- **Tier**: 3 (architecture / robustness)
- **Affected files**: `app/services/avatar_service.py` (`upload_avatar`,
  `_finalize_avatar_file`)
- **Verification method**: read `upload_avatar` and `_finalize_avatar_file` directly;
  confirmed the filesystem mutation precedes both the DB `UPDATE` and the
  transaction's `commit()`.

## Risk assessment
Low real-world likelihood: this only manifests if a *later* step in the same
`_write_transaction` block fails, or the `commit()` call itself fails — the normal,
successful request path (the only path this route exercises today, since nothing
else runs inside that transaction block after the avatar upload) is unaffected. Not
urgent for a solo local-use app, but a legitimate correctness gap if this route is
ever extended to do more inside the same transaction.
