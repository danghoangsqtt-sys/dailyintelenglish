## Summary
`AIWorker._run_loop` (`app/services/ai_worker.py:92`) has no `try/except` around
`_claim_next()` / `_process()`. `_process` guards the handler, but its own recovery
write (`transition_status(... "error")`, line 127) and `_claim_next`'s write
transaction are unguarded. Any exception there — for example a transient
`sqlite3.OperationalError: database is locked` while the owner has `data/app.db` open in
a DB browser, a full disk, or an illegal-transition `ValidationError` if a handler raises
after already committing a terminal status — ends the asyncio task. Nothing logs it
(the task has no done-callback) and nothing restarts it.

## Details
Failure mode: the HTTP server keeps running and `/health` reports OK, but every
new script/learning job stays `pending` forever until the app is restarted. The user
sees only a spinner that never finishes.

## Acceptance Criteria
- [ ] `_run_loop` catches `Exception` per iteration, logs it with `logger.exception`, backs off (e.g. the poll interval) and continues; it never swallows `CancelledError`.
- [ ] The error-transition inside `_process`'s `except` is itself guarded, so an illegal transition is logged rather than raised.
- [ ] A test: `_claim_next` raises once, then the loop still claims and completes a later job.
- [ ] Optional: `/api/ai/health` (or `/health`) reports whether the worker task is alive.
