## Summary
`app/services/project_service.py::update_speaker` (called from
`PATCH /api/projects/{id}/speakers/{speaker_id}`) updates a speaker's
`tts_engine`/`voice_description`/`speed`/`pitch`/`volume` in place, but never checks
or changes the project's `status`, and never touches `audio_jobs`/`video_jobs` or any
script line's `audio_cache_path`. PM independently confirmed via direct code read:
every field `SpeakerUpdate` can change directly affects TTS synthesis output — there
is no cosmetic-only field on this model (name/gender/accent are deliberately excluded
from it, per its own docstring).

This is the same class of bug as `BUG-013` (script edits not invalidating downstream
status, fixed under Task 7.1) — just reached through a different mutation path (voice
settings instead of script text) that Task 7.1's scoping missed.

**Mitigating factor found during PM's re-verification** (not present in the original
report): the actual audible/downloadable output is not permanently wrong, because
both real consumption paths — the per-line "Listen" button
(`frontend/static/js/step4_tts.js::previewLine`) and "Generate All"
(`generateAll`) — always call `Api.previewTtsLine()` for every line before playing or
mixing, which always re-synthesizes fresh audio using the *current* speaker settings
(`tts_service.py::synthesize_line`, no cache-skip logic). So a user who actually plays
or downloads audio after changing voice settings gets correct audio. The real gap is
purely the `status` field claiming "complete" (or any downstream status) when the
already-generated MP3/MP4 *file* on disk no longer matches current settings until
Generate All is re-run — an honesty/signal gap, not a wrong-output gap.

## Details
- **Tier**: 3 (correctness anti-pattern)
- **Verification method**: read `update_speaker`, `SpeakerUpdate`, `synthesize_line`,
  `preview_line` (API), and `step4_tts.js`'s `previewLine`/`generateAll` directly.

## Fix direction (see Task 9.1 for the full plan)
Reuse the *downstream-downgrade* half of Task 7.1's `mark_script_changed()` logic
(audio_generated/video_generated/complete -> script_generated, non-destructive), but
**not** its draft-advance half — a speaker can legitimately be edited at Step 1
config time, before any script exists, and must not spuriously advance the project to
`script_generated`. See the task card for the exact design decision on how to share
this logic without introducing that regression.

## Acceptance Criteria
- [ ] Editing a speaker's voice settings when the project is already at

- [ ] Editing a speaker's voice settings when the project is at `draft` or
      `script_generated` does NOT change status (no regression to the draft-stage
      Step 1 config flow)
- [ ] Add a test proving both cases
