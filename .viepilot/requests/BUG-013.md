## Summary
`app/services/project_service.py::_validate_status_transition` enforces a strict
forward-only, one-step-at-a-time project status machine
(`draft -> script_generated -> audio_generated -> video_generated -> complete`),
confirmed via direct read (lines 45-59). However, the two script-editing endpoints —
`POST /{project_id}/script/generate` and `POST /{project_id}/script/regenerate`
(`app/api/projects.py` lines 213-243) — carry **no status guard at all** (the code
itself is commented `# no lock held — Gemini call`, referring to concurrency, not to
a status check). `_advance_to_script_generated` only acts when the current status is
exactly `"draft"` (a no-op otherwise) — it never blocks the call when the project has
already advanced past `script_generated`.

Net effect: a user can regenerate the full script or a single line at any time,
including after the project already has `audio_generated`/`video_generated`/`complete`
status with real generated audio/video artifacts on disk tied to the *old* script.
Nothing downgrades the project's status, invalidates the stale audio/video, or warns
the user that the downstream artifacts no longer match the current script.

## Reproduction
1. Create a project, generate script, generate audio, generate video (status now
   `video_generated` or `complete`).
2. Call `POST /{project_id}/script/regenerate` (or `/script/generate`) again.
3. Observe: call succeeds, script line(s) change, project status is unchanged, no
   error, no warning. The already-generated audio/video files still reflect the old
   script text.

## Risk assessment
Low *current* real-world risk for this solo local-use app (the one user is unlikely to
go back and edit a finished script by accident), but a genuine data-integrity gap: the
UI gives no signal that downstream artifacts are now stale, and there's no way to
force a clean re-generation of just the affected downstream steps.
