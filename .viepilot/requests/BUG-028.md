# BUG: Bulk approval fails when the running API is stale

## Meta
- **ID**: BUG-028
- **Type**: Bug
- **Status**: done
- **Severity**: high
- **Created**: 2026-10-09
- **Affected**: Activity Library bulk approval, running FastAPI process, browser error handling

## Summary
Clicking **Approve pending in view** reports `Request to /api/visuals/library/activities/approve-batch failed` and does not approve the selected pictures.

## Actual Behavior
The browser loads the updated Activity Library page and submits the new endpoint, but the running server returns 404. Its live `/openapi.json` lacks `/api/visuals/library/activities/approve-batch` even though the endpoint exists in `app/api/visuals.py`. The server was started without `--reload` before the new route was added. The API client hides the FastAPI `detail` field and displays a generic error.

## Expected Behavior
Pending pictures can be approved after owner confirmation even when the running API predates the batch route. The UI reports progress and any partial completion.

## Steps to Reproduce
1. Keep the old non-reloading Uvicorn process running on port 8000.
2. Load the updated `/shots` page.
3. Click **Approve pending in view** and confirm.

## Error Messages
`Request to /api/visuals/library/activities/approve-batch failed`

## Acceptance Criteria
- [x] Fall back to the existing per-picture review route when the batch route returns 404 or 405.
- [x] Show progress and accurate partial completion if a fallback request fails.
- [x] Do not submit any review mutation against the real activity database during verification.
- [x] Verify normal batch behavior and the stale-server fallback using isolated test data.

## Fix
The browser now tries batch approval first. If the running server lacks that route, it approves the selected pending pictures one at a time through the existing review endpoint. It reports progress and the completed count if a later request fails; retrying picks up only remaining pending pictures. The page's script URL now includes a version suffix so a page reload loads the fix. An isolated browser test covers 404 fallback, a failed second request, and retry. The targeted Activity Library suite passes (18 tests), and the live server serves the updated JavaScript. No real approval request was sent during verification. Automatic approval review blocked restarting the existing Uvicorn process, so the process still lacks the new route; the fallback works with that process.
