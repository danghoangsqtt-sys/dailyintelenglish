# BUG: A failed audio/video regeneration attempt destroys the DB record of a still-valid previous success

## Meta
- **ID**: BUG-017
- **Type**: Bug
- **Status**: done
- **Priority**: high (real, unconditional data-loss-from-the-DB's-perspective on every
  regeneration failure that follows a prior success — elevated from Codex's original
  "medium" after PM's independent re-verification found the impact is more severe
  than a metadata inconsistency)
- **Created**: 2026-09-18
- **Reporter**: Codex (parallel read-only vp-audit pass, requested alongside PM's own audit)
- **Assignee**: TBD (Phase 9 / Task 9.1)
- **Source**: Codex's independent read-only audit, independently re-verified and
  re-scored by PM

## Summary
`app/services/audio_service.py::save_audio_job` and
`app/services/video_service.py::save_video_job` are both full-column UPSERTs
(`INSERT ... ON CONFLICT(project_id) DO UPDATE SET col = excluded.col` for **every**
column, including `mp3_path`/`wav_path`/`timestamps_json`/`duration_seconds`/
`loudness_lufs` for audio, and `mp4_path`/`mp4_path_vertical`/`srt_path` for video).

`app/api/audio.py`'s and `app/api/video.py`'s `except Exception` handlers call these
same functions with **only** `status="error"` and `error_message=str(exc)` — every
other keyword argument defaults to `None`. PM confirmed via direct code read that the
UPSERT's `excluded.column` clause unconditionally overwrites every column with these
defaults, meaning:

**If a project already has a successful audio (or video) job, and the user attempts
to regenerate it (e.g., after changing a voice setting or background music) and that
attempt fails for any reason** (TTS error, ffmpeg failure, disk issue, etc.), the
previous job's `mp3_path`/`wav_path`/`duration_seconds`/etc. are wiped to `NULL` in
the database — **even though the actual MP3/WAV (or MP4/SRT) files from the earlier
successful generation are still sitting on disk, untouched.** The user's UI would now
show a failed/empty state with no working download link, while a perfectly good
previous output is orphaned on disk, unreachable via the API
(`download_audio`/`download_video` require `job["status"] == "complete"` and a
non-null path).

Codex reproduced this for both audio (MP3/WAV) and video (MP4/SRT) job tables.

## Details
- **Tier**: 3 (correctness anti-pattern — real potential data/UX loss)
- **Affected files**: `app/services/audio_service.py` (`save_audio_job`),
  `app/services/video_service.py` (`save_video_job`), `app/api/audio.py`
  (`generate_audio`'s except block), `app/api/video.py` (`generate_video`'s except
  block)
- **Verification method**: read all 4 files directly; confirmed the UPSERT's SET
  clause touches every column unconditionally on both tables.

## Fix direction (see Task 9.1 for the full plan)
Add a narrow function per service (e.g. `mark_audio_job_failed(db, project_id,
error_message, commit)` / `mark_video_job_failed(...)`) that **only** updates
`status`, `error_message`, and `completed_at` via a plain `UPDATE ... WHERE
project_id = ?` — preserving every other column's existing value. If no row exists
yet (a genuinely first-ever attempt, nothing to preserve), fall back to inserting a
fresh error-only row. Route both API error handlers to call this new function instead
of the full-replace `save_audio_job`/`save_video_job`.

## Acceptance Criteria
- [x] A failed regeneration attempt after a prior success preserves the prior job's
      file paths/duration/timestamps/etc. in the DB — only `status`/`error_message`/
      `completed_at` change
- [x] A failed *first-ever* attempt (no prior job) still records a sensible
      error-only row, as today
- [x] The previously-successful file remains downloadable via the API after a
      subsequent failed regeneration attempt
- [x] Add a test reproducing the current data loss and proving the fix, for both
      audio and video
- [ ] Re-run vp-audit: this finding no longer appears (not yet re-run since the fix)

## PM Acceptance
Verified 2026-09-18 under Phase 9 / Task 9.1
(`.viepilot/phases/09-regeneration-integrity/tasks/task-9.1.md`): new
`mark_audio_job_failed()`/`mark_video_job_failed()` narrowly update only `status`/
`error_message`/`completed_at`, preserving every other column; the API error
handlers now call these instead of the old full-replace `save_audio_job`/
`save_video_job`. `download_audio`/`download_video`'s status gate correctly widened
to keep a preserved prior success downloadable after a later failure. Real end-to-end
tests generate actual audio/video, save the real response bytes, force a second
attempt to fail, and confirm the download endpoint returns the identical bytes
afterward — proving the fix at the byte level a user would actually experience.
Zero real defects found on PM's independent review. **Accepted.**
