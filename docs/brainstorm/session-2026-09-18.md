## Phases

### Phase 13 — Provider-Independent AI Reliability and Long-Running Generation (proposed)

- **Task 13.1 — Central generation gateway and correct resilience policy**
  - Replace four duplicated direct-REST implementations in `script_service.py`,
    `learning_service.py`, `thumbnail_service.py`, and `youtube_service.py` with one
    provider-neutral generation gateway.
  - Define a small provider contract for schema-constrained generation, health/model
    discovery, usage metadata, cancellation, and normalized errors. Initial adapters:
    local Ollama and Gemini via the official `google-genai` SDK.
  - Make one layer solely responsible for transport retries.
  - Retry transient transport failures (`TimeoutException`, connect/read/network
    errors), HTTP 408/429, and HTTP 5xx with randomized exponential backoff.
  - Use a global retry/deadline budget so SDK retries and model fallbacks cannot
    multiply into an uncontrolled attempt storm.
  - Add structured diagnostics: exception type + `repr`, model, attempt, latency,
    prompt hash, interaction ID, status, and input/output/thought token counts. Never
    log API keys or full prompts.

- **Task 13.2 — Durable provider-neutral generation job**
  - Move script and learning generation behind persisted jobs so neither local GPU
    inference nor a cloud request holds the browser/API connection open past 60 seconds.
  - For Gemini, use the Interactions API with `background=true`; for Ollama, persist
    local job state and execute inference in a bounded worker.
  - Persist the remote interaction ID when applicable and local job state in SQLite;
    poll with short HTTP requests.
  - Add start/status/cancel semantics and UI states that survive page refresh and app
    restart.
  - Store a project-config/prompt hash with the job so a result is not applied if the
    project configuration changed while Gemini was running.
  - Allow only one active generation job for the same project + operation + prompt
    hash; save validated output atomically.

- **Task 13.3 — Local-first model policy and degraded fallback**
  - Remove Gemini 3.8 Flash as the default for script/learning generation.
  - Proposed initial production route: `Qwen3.5-9B` 4-bit through Ollama as the local
    primary, one bounded same-model repair pass for invalid semantic output, then
    stable `gemini-3.5-flash` as the cloud fallback.
  - Keep `gemini-3.5-flash-lite` behind quality gates for lightweight operations only.
    Do not place preview/experimental aliases in the production fallback chain; run
    them only as explicitly selected canaries.
  - If background jobs still fail repeatedly, degrade to checkpointed generation:
    outline first, then 1–2 minute sections, followed by deterministic merge and global
    validation for word count, line IDs, speaker balance, and repetition.
  - Add real operational canaries for 1, 5, 8, and 10 minutes. Acceptance includes no
    duplicate active jobs, refresh/restart recovery, valid structured output, transparent
    failure messages, and a successful full TTS/audio/video pipeline for 8–10 minutes.

- **Task 13.4 — Reproducible local-model bake-off before rollout**
  - Run the exact existing prompts and Pydantic schemas against pinned model digests,
    not mutable `latest` tags.
  - Primary candidate: `Qwen/Qwen3.5-9B`; quality challenger:
    `google/gemma-3-12b-it-qat-q4_0-gguf`; Vietnamese learning-content challenger:
    `aisingapore/Apertus-SEA-LION-v4-8B-IT` using a verified 4-bit build.
  - Execute at least five runs for B1 5/8/10-minute scripts plus A2 and C1 samples.
    Measure first-token latency, total latency, peak VRAM/RAM, schema validity, target
    word-count error, speaker balance, repeated n-grams, CEFR suitability, EN–VI
    learning accuracy, and downstream Edge TTS duration.
  - Promote only a model that completes the 8-minute end-to-end run repeatedly. Keep
    only the winner installed in the default path; challengers remain benchmark options.

## Topics Discussed

### Topic 1: Evidence and root-cause analysis

**Context**: Changing the API key did not fix generation. Google AI Studio showed
approximately 1.145K Gemini 3.8 Flash tokens used, while the app returned HTTP 502.

**Measured evidence**:

- The newly saved key is active: `GET /api/settings` reports `source="database"`.
- The exact 8-minute project prompt is 4,562 characters / 702 whitespace-delimited
  words.
- Gemini `countTokens` reports 1,189 input tokens for that prompt.
- This is close to the reported 1.145K usage, so the dashboard number is consistent
  with input prompt processing; it is not evidence that a complete script response was
  generated and lost.
- The real operational trial produced two read timeouts near the hardcoded 60-second
  boundary and one attempt sequence where the first call returned 503, then the retry
  timed out.
- A direct minimal request to `gemini-3.8-flash` returned HTTP 503 “high demand”; a
  minimal request to `gemini-3.7-flash` also timed out.
- Replacing the key changes authentication/quota identity but does not remove model
  overload, default thinking latency, or the application's 60-second read timeout.

**Code findings**:

- All four Gemini services instantiate a fresh `httpx.AsyncClient(timeout=60.0)` per
  attempt.
- `httpx.RequestError`, including `ReadTimeout`, is immediately converted to an app
  error. It neither retries nor moves to the next fallback model.
- Only HTTP 429 and 503 are retried. Tests explicitly encode HTTP 500 as non-retryable,
  contrary to current Google guidance for transient 5xx failures.
- Backoff is fixed at 1/2/4 seconds with no jitter.
- Retry logic is duplicated across four services, so any fix must otherwise be copied
  and kept synchronized four times.
- The fallback chain can make up to 24 inference attempts (4 attempts × 6 models) for
  status-based failures, while making only one attempt for a network timeout. Both
  extremes are undesirable.
- `str(httpx.ReadTimeout)` is commonly empty, explaining the unhelpful API error
  `"Gemini API request failed: "`.

**Root-cause conclusion**:

1. **Immediate external trigger**: Gemini model capacity/high-demand latency.
2. **Latency amplifier**: Gemini 3.x thinking is enabled by default; 3.8 Flash defaults
   to medium thinking and is optimized for long-horizon/agentic work rather than this
   routine drafting workload.
3. **Primary application defect**: a legacy synchronous full-response request with a
   fixed 60-second read timeout for a long structured output.
4. **Resilience defect**: transport timeouts bypass retry and model fallback entirely.
5. **Operational visibility defect**: no durable job ID/token breakdown and empty
   exception messages obscure whether Gemini is queued, running, failed, or completed.

### Topic 2: International research

**Official Google findings**:

- Gemini troubleshooting recommends retrying timeouts, network failures, 408, 429, and
  5xx with exponential backoff and jitter. The official Python SDK includes automatic
  transient-error retries.
- Gemini API errors define 503 as temporary overload/down and 504 as a deadline issue.
- Google documents that standard long HTTP requests commonly close around 60 seconds;
  the Interactions API with `background=true` returns an interaction ID and supports
  polling, streaming/reconnection, cancellation, and terminal job states.
- As of June 2026, Google recommends Interactions API for new work and labels
  `generateContent` legacy, while still supported.
- Interactions supports structured JSON output, including streamed partial JSON.
- Gemini 3.x models enable thinking by default. For Gemini 3.8 Flash, `medium` is the
  default and `low` is recommended for latency-sensitive drafting/incident workflows.
- Failed 400/500 requests are not billed for tokens, but still count against quota.
  Therefore “used tokens” in the usage dashboard does not automatically mean a billable
  successful output.

**International reliability guidance**:

- Google SRE warns that retries can amplify overload and recommends randomized
  exponential backoff, per-request retry limits, and a retry budget.
- AWS Builders' Library emphasizes making retryable operations idempotent and avoiding
  retry multiplication across layers.

### Topic 3: Options and recommendation

| Option | Benefit | Limitation | Decision status |
|---|---|---|---|
| Raise timeout to 180–300 seconds | Small patch; may make today's request pass | UI stays blocked; no restart/resume; timeout can still duplicate remote work | Reject as sole fix |
| Stream legacy `generateContent` | Avoids waiting for the complete body before receiving bytes | API is now legacy; reconnect/job persistence remain weak | Acceptable tactical bridge only |
| Official SDK + corrected retry/fallback | Fixes timeout/5xx policy and removes duplicated custom transport logic | Still insufficient if the request remains synchronous | Required foundation |
| Interactions background job + polling | Directly solves the documented 60-second connection problem; supports durable state/cancel/observability | Requires DB/API/UI job lifecycle changes | Recommended core solution |
| Generate 1–2 minute chunks | Limits per-call latency and checkpoints progress | More calls, more quota, merge/coherence/speaker-balance complexity | Degraded fallback only |
| Provisioned Throughput / Vertex AI | Predictable reserved capacity | Cost and infrastructure are disproportionate for a local single-user app | Not recommended now |

**Proposed decision**:

- Adopt **official SDK + Interactions background execution + persisted job state** as
  the durable fix.
- Add **low thinking**, bounded output, a short model fallback chain, global retry
  budget, jitter, and a circuit breaker/degraded mode.
- Do not treat a longer timeout or another API key as the final solution.

### Topic 4: Open-weight and lower-tier model strategy

**User direction**: Stop relying on Gemini 3.8 Flash as the default; investigate lower,
more stable Gemini models and GitHub/Hugging Face models that can cover both podcast
script generation and bilingual learning content.

**Local hardware and runtime facts**:

- The machine has an NVIDIA GeForce RTX 3060 with 12,288 MiB VRAM.
- Ollama is not currently installed.
- The existing script output is a nested list of line objects and the learning pack is
  a nested object containing vocabulary, idioms, grammar, and questions. Grammar-level
  JSON constraint is necessary but not sufficient; every result must still pass current
  Pydantic validation plus semantic checks.

**Model shortlist**:

| Candidate | Fit for this project | 12GB feasibility | Main caveat | Proposed role |
|---|---|---:|---|---|
| Qwen3.5-9B | Apache-2.0; 201 languages/dialects including Vietnamese; 256K context; official Ollama package is 6.6GB | Strong | Newer architecture requires a current runtime; long-form/CEFR quality still needs a project-specific bake-off | Primary candidate for both script and learning |
| Gemma 3 12B IT QAT | 140+ languages; 128K context; 8,192-token output; QAT designed to preserve BF16-like quality | Viable but tight: official Ollama QAT package is 8.9GB | Custom Gemma terms; less VRAM headroom for large KV cache | Quality challenger / secondary local model |
| Apertus SEA-LION v4 8B IT | MIT; explicitly post-trained/evaluated for Vietnamese and other SEA languages; 65K context | Likely with a verified 4-bit quantization | Official card warns it is not safety-aligned; smaller runtime ecosystem and no official Ollama package found | Learning-pack/Vietnamese challenger, not default yet |
| Mistral-Nemo-Instruct-2407 12B | Apache-2.0; 128K; mature text model | Viable at 4-bit | Official language list/benchmarks do not establish Vietnamese support; older model | Exclude from first bake-off |

**Gemini policy finding**:

- Google's current model guide explicitly says most production apps should use a
  specific stable model. Preview models may have tighter rate limits and can be
  deprecated with as little as two weeks' notice.
- Therefore a preview model is not a reliability fix. `gemini-3.5-flash` is the more
  appropriate stable cloud fallback for routine, high-throughput drafting;
  `gemini-3.5-flash-lite` should be admitted only if the quality bake-off passes.
- Any preview model may be exposed as an opt-in canary for comparison, never as an
  automatic fallback that silently changes production behavior.

**Architecture conclusion**:

1. A model swap alone does not fix the synchronous 60-second design defect. Local
   generation must use the same durable start/status/cancel job lifecycle.
2. Start with one local model, not a permanent chain of several large downloads:
   Qwen3.5-9B is the best first candidate for the installed 12GB GPU.
3. Generate an outline and bounded sections, then merge and validate. This limits a
   failed generation to one checkpoint and improves coherence control for 8–10 minutes.
4. Constrain JSON at inference, then run Pydantic and semantic validation. A single
   repair pass may fix validation failures; after that, route to the stable cloud
   fallback instead of retrying indefinitely.
5. Pin model name, quantization, runtime version, and content digest. Local weights
   eliminate provider overload but do not eliminate model/runtime regressions.

### Topic 5: Should this workstation run generation locally?

**Measured workstation headroom**:

- GPU: NVIDIA GeForce RTX 3060, 12,288 MiB VRAM; approximately 11,343 MiB was free
  during the assessment.
- System RAM: 31.7 GiB total; approximately 21 GiB free.
- Storage: approximately 238 GiB free on drive D.

**Recommendation**: Yes — use local generation, but deploy it as **local-first hybrid**,
not local-only.

**Rationale**:

- The official Ollama Qwen3.5-9B package is about 6.6GB, leaving materially more GPU
  headroom than the 8.9GB Gemma 3 12B QAT package for KV cache, runtime buffers, and
  the Windows display workload.
- Local inference removes the external 503/capacity and per-model quota failure modes
  that blocked the operational trial, gives predictable marginal cost, and keeps
  podcast prompts on the workstation.
- A 9B 4-bit model may still be weaker than Gemini on long-range coherence, precise
  CEFR control, IPA, and difficult structured-output semantics. The stable cloud
  fallback is therefore retained until repeated real trials prove local-only quality.
- Local inference does not solve the current synchronous-request defect: generation
  remains a long-running job and must expose start/status/cancel/recovery semantics.

**Initial operating envelope**:

- Run one inference model at a time: `qwen3.5:9b`, 4-bit, pinned digest.
- Start with a 16K context allocation rather than the advertised 256K maximum; the
  existing 8–10 minute script workload does not need a huge context and KV cache must
  remain bounded on 12GB VRAM.
- Generate an outline and bounded dialogue sections, checkpoint each section, then
  merge and validate. Do not request a monolithic 8–10 minute nested JSON response.
- Use constrained JSON plus existing Pydantic validation. Add deterministic checks for
  target words/duration, valid speaker IDs, speaker balance, repetition, CEFR features,
  and bilingual learning fields.
- Permit one local repair attempt. On runtime failure or repeated validation failure,
  route explicitly to stable `gemini-3.5-flash`.
- Do not generate script/learning concurrently with another local LLM request. Release
  the model after the learning stage when GPU memory is needed elsewhere.

**Go/no-go gate for local primary**:

- Five consecutive valid 8-minute generations without crash or unrecoverable schema
  failure.
- At least four of five stay within the agreed word-count/duration tolerance and pass
  speaker/CEFR/repetition checks.
- Learning packs pass human review for Vietnamese meaning, IPA, grammar explanation,
  and answer-key correctness.
- The full winning run completes TTS, audio mix, and video render successfully.
- If these gates fail, keep local as an optional/offline mode and use stable Gemini 3.5
  Flash as the production primary until a better local model or prompt pipeline passes.

#### Work package 13.2 — Introduce the provider-neutral AI gateway

**Dependencies**: 13.0; may proceed while 13.1 is benchmarked. **Effort**: 1–1.5 days.

**Proposed files**:

- `app/services/ai/contracts.py`: provider request/result types and capability flags.
- `app/services/ai/ollama_provider.py`: localhost Ollama adapter using existing `httpx`.
- `app/services/ai/gemini_provider.py`: official `google-genai` adapter and Gemini
  background interaction support.
- `app/services/ai/router.py`: task-aware provider selection, retry budget, circuit
  breaker, fallback reason, and metrics.
- `app/services/ai/validation.py`: shared parse/schema/semantic validation utilities.
- `app/services/ai/errors.py`: normalized error codes such as `provider_unavailable`,
  `timeout`, `rate_limited`, `invalid_output`, `cancelled`, and `stale_result`.

**Rules**:

- Services request a capability (`script`, `line_rewrite`, `learning`) rather than
  importing provider-specific clients.
- Retry only transport errors and documented transient statuses. Use jittered backoff
  and one global time/attempt budget; never multiply retries in provider and router.
- Local failure policy: one infrastructure retry or one semantic repair, then one
  stable cloud fallback. No six-model cascade.
- Logs include job ID, provider, pinned model/digest, prompt hash, stage, attempt,
  latency, token/eval counts when available, validation failure, fallback reason, and
  exception type/`repr`; never log API keys or full prompts.

**Exit criteria**: script and learning services can use a fake provider in unit tests;
Ollama and Gemini share one normalized result/error contract.

#### Work package 13.3 — Add durable AI jobs and a single local worker

**Dependencies**: 13.2. **Effort**: 1.5–2 days.

**Database migration**: add `006_ai_generation_jobs.sql` with:

- `ai_generation_jobs`: ID, project ID, operation, status, provider/model, prompt and
  config hashes, progress/stage, attempt/fallback metadata, cancel flag, remote
  interaction ID, error code/message, metrics JSON, and timestamps.
- `ai_generation_checkpoints`: job ID, section index, status, input hash, validated
  result JSON, metrics JSON, and timestamps.
- A partial unique index preventing more than one active job per project + operation.
- Foreign keys with cascade on project deletion; no destructive changes to existing
  script/learning tables.

**Job states**:

`pending → running → validating → complete`, with terminal alternatives `error`,
`cancelled`, and `stale`. A `fallback` stage is recorded in metadata, not hidden.

**Worker design**:

- One in-process `asyncio` worker/semaphore is sufficient for this single-user desktop
  app; Celery/Redis is not introduced.
- Move the shared SQLite transaction lock/helpers out of `app/api/projects.py` into a
  DB-layer module so routes and the background worker use the same short transaction
  boundary without importing an API router.
- Never hold the DB lock during model inference. Snapshot inputs, release the lock,
  generate, then atomically validate/save under a short write transaction.
- Startup recovery scans non-terminal jobs. Script jobs resume after the last validated
  checkpoint if hashes still match; learning jobs restart once. Mismatched project
  configuration marks a job `stale` rather than overwriting newer edits.
- Cancellation closes the local HTTP stream/task and checks between sections; Gemini
  calls its interaction-cancel operation when a remote ID exists.

**Proposed API**:

- `POST /api/projects/{id}/ai-jobs` with `{operation: script|learning}` → HTTP 202 job.
- `GET /api/projects/{id}/ai-jobs/active?operation=...` → refresh recovery.
- `GET /api/projects/{id}/ai-jobs/{job_id}` → status/progress/error/result readiness.
- `POST /api/projects/{id}/ai-jobs/{job_id}/cancel` → idempotent cancellation.
- Existing `POST .../script/generate` and `POST .../learning/generate` remain available
  behind compatibility mode during rollout; the UI moves to the new API first.

**Exit criteria**: duplicate starts are idempotent, refresh resumes polling, restart
recovers a checkpointed job, cancel is terminal, and stale output cannot overwrite data.

#### Work package 13.4 — Restructure script generation into checkpoints

**Dependencies**: 13.2–13.3. **Effort**: 1.5–2 days.

- Split prompt templates into `outline`, `section`, and `repair` stages while reusing
  existing genre and CEFR fragments.
- Compute target words deterministically from the CEFR WPM file × requested duration.
  For B1 8 minutes, the existing rule yields about 800 spoken words.
- Produce an outline containing section objectives, target words, speaker allocation,
  required language features, and intro/outro placement.
- Generate sections of roughly 1–2 minutes. Feed each section a compact summary of the
  outline and prior section, not the entire raw generation trace.
- Generate line IDs server-side after merge. The model must choose only supplied
  speaker UUIDs; it should not invent identifiers.
- Run section checks before checkpointing: schema, allowed speaker, word range,
  consecutive-turn limit, requested language-feature policy, and topic relevance.
- Run global checks after merge: total word tolerance, speaker balance, duplicated
  phrases/n-grams, intro/outro, line ordering, and CEFR heuristic warnings.
- On a repairable failure, send only the failing section and explicit validation errors
  for one repair pass. Then route to cloud or fail transparently.
- Persist the complete script and advance project status only after all sections pass;
  never expose a half-written script as the current project script.

**Initial generation settings**:

- Script temperature: approximately 0.4–0.6, tuned by benchmark.
- Context: 16K; per-section output bounded to the required word/token envelope.
- Ollama structured `format` schema plus Pydantic and semantic validation.

**Exit criteria**: local generation produces a complete valid 5- and 8-minute B1 script,
and an injected section failure resumes from the last checkpoint.

#### Work package 13.5 — Harden learning-pack generation

**Dependencies**: 13.2–13.4. **Effort**: 1 day.

- Generate the pack only from the persisted final script and store its script hash on
  the job. Script edits during generation make the result stale.
- Keep one structured call initially because the transcript and pack are smaller than
  the script workflow; split into vocabulary/idiom and grammar/question stages only if
  measured latency or validity requires it.
- Use low temperature (approximately 0–0.2) and the existing `LearningPackOut` schema.
- Add grounding checks: every vocabulary/idiom phrase and quoted example must occur in
  the transcript after normalization; answers must correspond to their options; counts
  remain within requested ranges.
- Treat IPA and Vietnamese meaning as quality-review fields. Do not label model output
  as dictionary-verified unless a deterministic dictionary source is added later.
- One targeted repair pass receives only failed items and validation messages.

**Exit criteria**: five packs validate structurally; human review records IPA,
Vietnamese, grammar, grounding, and answer-key defects per model.

#### Work package 13.7 — Cloud fallback and compatibility migration

## Summary

### Key decisions proposed

1. Treat this as a new Phase 13 reliability feature, not an API-key problem.
2. Migrate long script and learning generation to durable provider-neutral jobs;
   Gemini uses background interactions and local inference uses a bounded worker.
3. Centralize provider transport/retry/model policy across all four AI consumers.
4. Use `thinking_level="low"` for routine podcast generation.
5. Use checkpointed outline/section generation for 8–10 minute content and validate
   every merged result before persistence.
6. Proposed local-first policy: Qwen3.5-9B primary, stable Gemini 3.5 Flash fallback;
   preview Gemini models are canary-only.
7. Execute Phase 13 through two evidence gates: Gate A qualifies the local runtime;
   Gate B promotes local to production primary only after repeated real 8-minute runs.
8. Preserve legacy synchronous endpoints for one compatibility release and maintain a
   settings-only rollback to Gemini while the job-based API is proven.
