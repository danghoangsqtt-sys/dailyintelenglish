## Topics Discussed

### Topic 1: Review of the Coder's Gate B conclusion

**Coder's reported conclusion (Sonnet 5, Task 13.9):**
> Gate B FAIL. 8/9 script runs failed the ±15% section word-count validator. "This is NOT a
> system defect — the durable-job architecture works as designed. The problem is the local 9B
> model's word-count precision." Recommendation: ship Task 13.10 with Gemini-primary,
> local-experimental.

**What the Coder did well (verified, keep):**
- The trial was genuinely real — live `uvicorn`, real HTTP, real local inference, zero mocks.
- **No threshold was weakened to force a pass.** Correct governance under pressure.
- Self-disclosed its own runner's `has_outro` heuristic false negative rather than letting it
  inflate the failure count.
- Self-disclosed and fixed an infrastructure regression it had itself caused in Task 13.8
  (an Ollama restart that dropped the persisted `OLLAMA_MODELS` variable).
- Refused to run the media pipeline and recorded it as "not executed" rather than fabricating it.
- Clean state/doc/commit discipline throughout; git persistence gate honoured every task.

**Where the analysis was incomplete (three findings):**

1. **The cited evidence for "repair didn't help" does not exist.** The report stated the
   one-repair mechanism failed to correct the sections. `grep -rn "repair_count" app/` returns
   exactly one hit — the field declaration in `app/models/ai_job.py`. **Nothing in the codebase
   ever increments it.** The repair *is* called (`script_pipeline.py` lines 459–462), but there
   is zero telemetry on whether it ran, how often, or what it produced. The conclusion may be
   directionally right; the evidence offered for it was meaningless.

2. **Root cause analysis stopped one level too shallow.** It did not ask why a model that
   succeeds on most sections yields an 11% job success rate. See Topic 2.

3. **It declared the architecture sound without testing the architecture against the provider
   it recommended shipping.** The ±15%-per-section hard gate applies to *every* provider. Gemini
   was never run through Gate B. That unfalsified assumption is what Topic 3 disproves.

### Topic 2: The compounding-failure architecture defect (local provider)

`script_pipeline.py` hard-fails the **entire job** when any single section misses its word
budget by more than ±15%, after one repair attempt:

```python
if errors:
    section_lines, errors = await _repair_section(...)
if errors:
    await _fail(db, job_id, "section_validation_failed", errors)
    return
```

A B1 eight-minute script is 800 words ÷ 5 sections = 160 words per section. **Five independent
chances to kill the job.**

**Hard evidence from the `ai_generation_checkpoints` table** (each valid section is
checkpointed, so the per-section pass rate is directly measurable — this was not in the
Coder's report):

| Metric | Value |
|---|---|
| Sections attempted | 27 |
| Sections passed | 18 |
| **Per-section pass rate** | **66.7%** |
| Job-level pass rate | 11% (1/9) |
| Theoretical 0.667⁵ | **13.2%** — matches observed |

The model is not failing two thirds of the time; it is succeeding two thirds of the time, and
the architecture is compounding that into an 11% job success rate.

**Word-count distribution of accepted sections** (n=18): mean **145.9** vs target 160 — a
systematic **−9% bias** — with a standard deviation of 19.5. The model undershoots
consistently and varies widely, so a large minority of sections land just below the −15% floor.

**The decisive observation:** the one job that completed produced sections
`[137, 152, 163, 164, 165]` = **781 words total against an 800-word target — a −2.4% miss.**
Individual section errors cancel at the aggregate level. Meanwhile the *actual product
requirement* is ±10% on the **total** (720–880 words, `SCRIPT_GLOBAL_WORD_TOLERANCE = 0.10`).

**Therefore:** the ±15%-per-section rule is an internal implementation detail that, because it
must hold five consecutive times, is in practice **stricter than the product requirement it is
supposed to serve**. That is the defect.

**Note on repair effectiveness:** if the existing repair pass were working, effective
per-section success would be ~89% and job success ~56%. Observed is 11%, consistent with repair
contributing close to nothing — but this cannot be proven until 14.2 instruments it.

### Topic 3: Gemini also fails — and for a worse reason (provider comparison diagnostic)

The runner was extended with `--mode gemini --runs 2 --skip-samples` (default stays `local`;
partial runs are reported as `DIAGNOSTIC_ONLY` so they can never be quoted as a gate result).

**Result: 0/2 jobs completed. Neither failure was the word-count validator.**

```
error_code: handler_exception
ProviderUnavailableError: Gemini is temporarily overloaded (HTTP 503)
```

Jobs died after **9 seconds** and **24 seconds**.

**Is Gemini actually down?** Direct probe, three consecutive calls to
`gemini-3.8-flash:generateContent`: **`200 → 503 → 200`**. Gemini is healthy and serving; it
returns intermittent 503s under load — the ordinary transient condition every production client
is expected to absorb.

**Why the app cannot absorb it:** `grep -rn "sleep" app/services/ai/` returns **nothing**.
There is no backoff anywhere in the gateway. `AIRouter._attempt_with_one_retry` catches the 503
and re-fires **immediately**, milliseconds later, while the backend is still overloaded. Two
attempts, no delay, one model, then the durable job dies.

**This is a regression introduced by Task 13.7:**

| | Legacy path (pre-13.7) | New gateway (current) |
|---|---|---|
| Attempts per model | 4 (`GEMINI_MAX_RETRIES`) | **2** |
| Backoff | 1s → 2s → 4s (`GEMINI_RETRY_BASE_DELAY`) | **none** |
| Model fallbacks | 6 (`GEMINI_MODEL_FALLBACKS`) | **1** |
| Survives a transient 503 | almost always | **no** |

ADR-001 states Phase 13's own motivation: *"A real eight-minute script request reached the fixed
60-second timeout **and also observed provider 503 overload**."* **The rewrite made 503
resilience strictly worse than the code it replaced**, and it went unnoticed because Gate B only
exercised the local provider.

**Fairness to the ADR:** ADR-001 deliberately rejects *multiple automatic fallback models*
(unpredictable cost, quality and failure modes) — that decision is sound and should stand.
But rejecting a multi-model cascade is **not** the same as rejecting retry-with-backoff on
transient errors. Task 13.7 removed both. Only the cascade was intended.

### Topic 4: Why Task 13.10 must not ship yet

The Coder's recommendation — ship durable jobs with Gemini primary — rests on the assumption
that the Gemini path works. It does not. Shipping now would deliver a system whose **primary
path dies on the first transient 503**, which is precisely the failure that justified building
Phase 13 in the first place. The correct move is to fix P0, re-measure both providers honestly,
and then let the real evidence choose the rollout mode.

### Topic 5: The user's earlier suggestions, assessed

- **"Split the prompt into a staged pipeline instead of one big generation."** Already
  implemented and correct: `script_pipeline.py` does outline → per-section generation
  (~145–208 words each) → validate → repair → checkpoint → merge. The failure is *inside* those
  already-small steps, not caused by a lack of chunking. No change needed.
- **"Use gemini-3.5-flash-lite or a preview model; avoid 3.8."** Not applicable to either root
  cause — the local failure is provider-agnostic architecture, and the Gemini failure is a
  missing retry policy that would affect any model equally. `gemini-3.8-flash` was live-verified
  (real `models.list` + official docs) as a current stable, non-preview model. ADR-001
  explicitly bars preview models from automatic routing, learned from the forced
  `gemini-2.0-flash` shutdown. Recommendation: keep 3.8-flash; revisit only with a concrete
  cited source.

### Governance note on D4

The controlling plan forbids silently relaxing thresholds. D4 does **not** relax the product
threshold — global ±10% / 720–880 words is untouched. It removes an internal intermediate
hard-stop that was never a product requirement and which, through compounding, was enforcing a
*stricter* effective standard than the product demands. Because it touches files outside Task
13.9/13.10's allowed lists, the controlling plan and task cards must be amended **before** any
code changes.

## Addendum — 2026-09-21 (after Gate B-2): the owner drops Gemini

### Trigger

Gate B-2 (`docs/operations/phase14-gate-b2.md`): local 3/5 complete with every completed
script passing all content checks and zero infrastructure failures; Gemini 0/5, FAIL-INFRA,
for two independent reasons — a 503 storm longer than the backoff window, and a **free-tier
quota of 20 requests/day/model** that the matrix exhausted during run 3 (every retry counts).
The owner asked whether an API-key pool, finer chunking, or the UI could reduce quota use, and
whether local models are good enough. PM answers, all evidence-based:

- A key pool does not help: the quota is per Google Cloud *project*, so more keys in one
  project share one bucket; more projects to dodge the limit breaks the Gemini API terms;
  and a pool does nothing about 503s, which killed 3/5 jobs before quota ran out.
- Finer chunking is already in place (outline → 5 sections → repairs = 7–11 requests per
  job) and is *why* the daily request quota runs out faster; requests are counted, not size.
- The UI costs no quota: Gemini only ever returns JSON text; rendering is local.
- Local quality is not the problem: the three completed local scripts passed every content
  check; the two failures were a 2.5× over-length section surviving repair and the
  ">5 consecutive lines" structural rule — both targeted, fixable.
