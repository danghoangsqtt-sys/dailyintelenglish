## PM verification (before proposing a plan)

PM independently re-verified 4 of the report's most concrete/checkable claims against
the actual source before presenting anything to the user — 3 confirmed real, 1
confirmed a **false positive**:

1. **Theme flash (real)** — `music_library.html`, `step1_config.html`,
   `step6_thumbnail.html`, `step7_youtube.html` all hardcode
   `<html data-theme="dark">`; `theme.js` correctly defaults to light but only runs on
   `DOMContentLoaded`, after the browser already painted the hardcoded dark state —
   a real, visible flash for any user without a stored dark preference.
2. **No-project-id dead-end (real)** — all 6 of step2-7's "Missing project" error
   states are plain `textContent`, no actual link to the Dashboard.
3. **TTS range slider styling (real)** — `step4_tts.html` has zero thumb/track color
   rules for the speed/pitch/volume sliders; they render in each browser's own
   default appearance, not the app's purple accent.
4. **YouTube chapters "always estimated" (FALSE POSITIVE)** — traced the actual code:
   `youtube_service.py::generate_package()` already branches correctly and uses
   `real_chapters_from_timestamps()` (real measured `start_sec` values) whenever a
   completed audio job exists; `app/api/youtube.py` already fetches and passes real
   timestamps when available. Only a stale docstring comment inside the fallback
   function is out of date — not a functional bug, not worth a task.

The other 4 findings in the report (single-connection DB lock, unused Gemini
rate-limiter constant, forward-only project status machine, inline CSS
fragmentation) were not independently verified this round — all are either large
architectural changes (consistent with the already-deferred "Progress cancellation"/
LivePortrait precedent) or lower-priority cleanup, not proposed for this task.
